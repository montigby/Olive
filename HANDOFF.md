## 1. Current Architecture Overview

Family Branch is a private family tree / directory app. It is a **pnpm monorepo** with three layers:

### Storage (Supabase Postgres)

Two parallel person systems exist **side-by-side**. Both share the same UUID primary key.

| Table | Purpose |
|---|---|
| `persons` | The original, rich display table. Has every profile field (phone, address, social handles, birthday, etc.), `relationshipLabel`, `parentPersonId`, `familyUnitId`, `isAdmin`, `claimed`, invite tokens, visibility settings. This is what the app reads for member cards and profiles. |
| `family_units` | Top-level groupings. Each unit has one admin. |
| `accounts` | Auth credentials: email, bcrypt password hash, FK → persons. |
| `unit_link_requests` | Cross-unit linking system. |
| `people` | **NEW** — The relationship graph node table. Lightweight: `id`, `family_id`, `first_name`, `last_name`, optional `birth_date`, `death_date`, `gender`, `managed_by`. Same UUID as the corresponding `persons` row. |
| `relationships` | **NEW** — Explicit typed relationship edges. `from_person`, `to_person`, `type`, `start_date`, `end_date`. See edge direction convention below. |

### Backend (`artifacts/api-server`)

Express server bundled by esbuild to a single `api/index.js` file. Runs as a Vercel serverless function. Uses `@workspace/db` (Drizzle ORM + pg Pool) for all database access. Never imports `pg` directly — that package lives only in `lib/db`.

### Frontend (`artifacts/family-branch`)

React + Vite SPA. React Query + orval-generated hooks for API calls. ReactFlow for tree rendering. Auth token stored in `localStorage.getItem("oliveToken")`.

### Libraries (`lib/`)

| Library | Purpose |
|---|---|
| `@workspace/db` | Drizzle schema, `db` instance, `pool`, and the new `relationships.ts` data layer. Imported by the API server. |
| `@workspace/api-zod` | Zod request-body schemas (generated by orval from openapi.yaml). |
| `@workspace/api-client-react` | React Query hooks (generated by orval). |
| `@workspace/api-spec` | OpenAPI YAML source + orval config. |

## 3. Key Architecture Decisions

### Two Person Tables (Not One)
The `persons` table was never redesigned — it has too many callers. The `people` table was added alongside it as the source of truth for graph traversal only. Both share the same UUID. The `persons` table remains the display source; `people` + `relationships` is the graph layer.

### Edge Direction: `(from_person = child, to_person = parent)`
For all parent-type edges (`biological_parent`, `adoptive_parent`, `step_parent`), the convention is:
- `from_person` = the child
- `to_person` = the parent

This is consistent with "directed toward parent." **All traversal functions follow this exactly:**
- `getParents(personId)` → `WHERE from_person = personId` → returns `to_person` values
- `getChildren(personId)` → `WHERE to_person = personId` → returns `from_person` values
- `getAncestors` climbs `from_person → to_person` (child → parent direction)

**Do not reverse this.** It was broken in the original implementation and fixed after 5/6 tests were failing.

### Symmetric Types
`spouse`, `ex_spouse`, and `partner` are always stored as two rows: A→B and B→A. `addRelationship` handles this automatically.

### Spouse Uniqueness
Adding a new `spouse` edge automatically retires existing `spouse` edges as `ex_spouse` with an `end_date`. This means each person has at most one current spouse in the DB.

### Sync is Best-Effort
`syncPersonToRelationshipLayer` is wrapped in try/catch. If it fails, the primary `personsTable` insert still succeeds and the API returns 201. The relationship layer is supplementary.

### No `pg` Imports in `api-server`
esbuild bundles the API server and `pg` is not a direct dep there. Always use `import { db, pool } from "@workspace/db"`. Never `import pg from "pg"` inside `artifacts/api-server/`.

### No `drizzle-kit push` in Build
`drizzle-kit push` prompts interactively and can't run in Vercel's CI. Schema changes must be applied via a migration SQL file executed through an admin HTTP endpoint or via the Supabase dashboard SQL editor.

### Explicit Pairs Override Heuristic
The tree layout uses a label-based heuristic (`buildSpouseMap`) to pair spouses. DB relationships now seed this map first. Members already in an explicit pair are skipped by the heuristic. This gives a clean fallback for members added before the relationship layer.

## 4. Relationship Layer — Sync Rules

`syncPersonToRelationshipLayer` maps `relationshipLabel` → edge type:

| Label | Edge Created |
|---|---|
| `wife`, `husband`, `spouse`, `partner` | `spouse(personId ↔ adminId)` (symmetric) |
| `mom`, `mother`, `dad`, `father` | `biological_parent(adminId → personId)` (admin is child, new person is parent) |
| `son`, `daughter`, `child` | `biological_parent(personId → adminId)` (new person is child, admin is parent) |
| `brother-in-law`, `sister-in-law` + `parentPersonId` | `spouse(personId ↔ parentPersonId)` (the sibling identified by parentPersonId) |
| `nephew`, `niece` + `parentPersonId` | `biological_parent(personId → parentPersonId)` |
| `grandson`, `granddaughter`, `grandchild` + `parentPersonId` | `biological_parent(personId → parentPersonId)` |
| `brother`, `sister`, `grandparent`, `mother-in-law`, `father-in-law`, etc. | **No edge.** Cannot determine the other party without shared parent data. Layout heuristics handle these. |

## 5. Tree Layout Architecture (`tree.tsx`)

Three layout functions exist:

| Function | Used When |
|---|---|
| `layoutUnit` | Admin viewing their own tree |
| `layoutLayeredView` | Non-admin viewing the tree (viewer-centric) |
| `layoutPersonalView` | **Dead code** — was superseded by `layoutLayeredView`. Can be deleted. |

### ReactFlow Node Types
- `couple` — horizontal pair of spouses with a connecting heart/bar
- `child` — single person card for children/individuals
- `pill` — collapsed group node that expands on click

### How Explicit Pairs Work
1. On tree mount, `GET /api/family-units/:unitId/relationships` is called
2. Response: all relationship rows for the unit
3. All `spouse` type edges seed a `Map<string, string>` (person A → person B)
4. This map is passed into `buildSpouseMap` as `explicitPairs`
5. `buildSpouseMap` pre-seeds its output map with explicit pairs; the heuristic then only runs for members not already covered
6. `layoutUnit` also accepts `explicitPairs` and uses an `explicitSpouseIn` helper that takes priority over the heuristic within each sibling-group pass

## 10. Gotchas and Tricky Areas

### Edge Direction Is Counterintuitive
In `relationships`, `from_person` is the **child** and `to_person` is the **parent**. This is opposite to what you might expect from "from → to" phrasing. All traversal functions were initially written backwards and had to be fixed. Every time you touch this layer, double-check which column is which.

### `pg` Cannot Be Imported in `api-server`
esbuild bundles `api-server`. `pg` is an external dependency that only exists in `lib/db`. If you try to `import pg from "pg"` in any file under `artifacts/api-server/`, the build will fail with `Could not resolve "pg"`. Always go through `@workspace/db`.

### `drizzle-kit push` Cannot Run During Build
It prompts interactively. The Vercel build will hang or fail. Apply schema changes via a one-shot HTTP endpoint or Supabase SQL editor.

### `onConflictDoNothing` is Required in Sync
Multiple insert paths (AI chat, REST endpoint, backfill) can race on the same person. The `people` table insert uses `.onConflictDoNothing()` to handle re-runs cleanly.

### Spouse Uniqueness Can Cause Surprising Behavior
`addRelationship(..., "spouse")` deletes ALL existing `spouse` edges for both people and converts them to `ex_spouse`. If you call it twice for the same pair (e.g., in a re-backfill), the second call will see no existing edges (they were renamed to `ex_spouse` by the first call) and the `unique_edge` constraint on the `ex_spouse` rows will conflict. Use `ON CONFLICT DO NOTHING` when inserting spouse edges manually.

### `buildSpouseMap` Has Three Heuristic Passes
The label-based heuristic runs three passes in `buildSpouseMap`: (1) label-based couples, (2) parentPersonId-linked siblings, (3) alphabetical fallback. Each pass checks `used.has(id)` so once a person is paired, they're skipped. Explicit pairs are seeded before pass 1 runs.

### Admin-only Endpoints Use a Hardcoded Secret
`ADMIN_SECRET` defaults to `"olive-admin-2026"` if the env var is not set. This is intentional for local dev but should be set properly in production. Protect the backfill endpoint from being called accidentally — it's idempotent but makes 39+ DB calls.

### `formatPerson` Is Defined in `auth.ts` and Imported Elsewhere
The canonical `formatPerson` function lives in `artifacts/api-server/src/routes/auth.ts` and is re-exported. Other routes import it from there. Do not redefine it elsewhere.

## 13. Deployment

Deploys automatically on push to main via Vercel.

Build command:
```
pnpm install && pnpm --filter @workspace/api-server run build && pnpm --filter @workspace/family-branch run build
```

The API server bundles to `api/index.js` (esbuild). The SPA builds to `artifacts/family-branch/dist/public`.

**CRITICAL**: Never add `drizzle-kit push` to the build command. It prompts and hangs.

Required env vars in Vercel:
- `DATABASE_URL` — Supabase connection string with SSL
- `JWT_SECRET` — JWT signing key
- `OPENAI_API_KEY` — For Olive AI chat
- `ADMIN_SECRET` — (optional) defaults to `"olive-admin-2026"` — protect admin endpoints
- `APP_BASE_URL` — Used for invite URL construction
